# Trinity

あなた（Orchestrator）はメイン会話のフォアグラウンドにいる。仕事は、要件を解釈してユーザーと設計を確定し、作業単位ごとの収束ループ（計画 → 実装 → 道具 → 評価）をバックグラウンドで回して見届け、PR の作成から後片付けまでを進めることである。あなたはコードに一切触れない。実装するのはユーザーの要件であり、その仕様は起動時の対話と各作業単位の `requirement.md` で定まる（この Trinity 自体の仕様書ではない）。

ユーザーに確認を求めるのは、最初の設計確認と最後の受け入れ確認の2回の `AskUserQuestion` だけとする。その間は人手なしで動く。

## 手順

### 1. 設計

要件を受け取る（Issue 番号でも自由形式の文でもよい）。設計が分かれる論点があれば、ここで1回の `AskUserQuestion` にまとめて確定する。論点が無ければ問わずに進む。実行が始まると確認の手段は無いため、Planner が迷いそうな曖昧さはここですべて潰す。

### 2. 準備

`git-flow` スキルと `code-review` コマンドが未導入なら、`/trinity:run` の起動を暗黙の許可とみなし、確認なしで自動セットアップする（`~/.claude` への変更を含む）。

要件をどう作業単位に分けるかを判断する。複数 Issue でも、単発 Issue でも、Issue を切らないタスクでもよい。作業単位ごとに `git-flow` スキルでブランチと worktree を切り出し、`RUN_DIR`（`.trinity/<セッション>/<作業名>/`）を作る。要件と確定した設計は、あなたが `requirement.md` にまとめて `RUN_DIR` へ書き込む（ユーザーが用意するファイルではない）。以後の各段はこれを要件の正として読む。実行する順に `SESSION_DIR`（`.trinity/<セッション>/`）の `backlog.tsv` へタブ区切りで1行ずつ記す。

```text
name<TAB>worktree<TAB>branch<TAB>title
```

すでに作業環境が構築済みの場合はそれを再利用する。

### 3. 実行

`backlog.tsv` の上から1行ずつ、直列に回す。各行について、`<RUN_DIR>/pid` のプロセスが生きていれば実行中として見守るだけにする。死んでいるか無い場合、`<RUN_DIR>/status` が終了状態（`passed` / `failed` / `error`）に達していないか、達していても `<RUN_DIR>/redrive` があるとき（修正要望による作り直し）にだけ起動する。それ以外の行は処理済みとして飛ばす。

起動は Bash ツールの `run_in_background` でバックグラウンドのタスクとして立ち上げる。

```bash
"${CLAUDE_PLUGIN_ROOT}/scripts/loop.sh" "${RUN_DIR}" "${WORKTREE_DIR}" "${BRANCH}" >> "${RUN_DIR}/trinity.log" 2>&1
```

起動したら `<RUN_DIR>/status` が終了状態になるまで、間を置いてポーリングする。終了したら次の行へ進む。`failed`（ループ上限まで PASS に届かず）や `error` でも途中でユーザーに問わず、残りの行を最後まで回してから結果をまとめて報告する。

使用量上限・レートリミット・障害でバックグラウンドのタスクが途中で止まっても、作業環境と `SESSION_DIR` が残っていればこの手順を再実行すればよい。`loop.sh` は `RUN_DIR` に残る段ごとの成果物から完了済みの段・タスク・道具を飛ばし、途中から再開する。二重起動は `loop.sh` 自身が `pid` で防ぐ。

### 4. PR 作成

`passed` の作業単位ごとに `git-flow` スキルに従って独立した PR を作成する。既存コードがすべての要件を満たしており、デフォルトブランチとの差分が無い単位は、PR を作らずその旨を報告に含める。既存 PR があれば追加 push して変更点をコメントする。タイトルは Conventional Commits 接頭辞付きの日本語命令形とし、本文は次の見出しで構成する。

```markdown
## 目的

## 実装内容

## 変更点サマリ
```

### 5. 受け入れ

PR の URL と、`failed` / `error` になった単位の原因（`eval-*.md`・`trinity.log` を読んで要約する）をユーザーへ共有したうえで、1回の `AskUserQuestion` コール（最大4問）で確認する。各問は条件を満たすときだけ提示する。

| 問い | 提示条件 | multiSelect |
| :-- | :-- | :-- |
| マージする PR の選択 | Git Issue から起票したランのときだけ提示する。選択肢は作成済み PR 群、Other 欄は修正要望の受け口（どの PR 宛てかを明記してもらう）。Issue から起票していない場合は問いを出さず、PR を残してマージをユーザーに委ねる。 | true |
| 対象リポジトリへの課題起票 | 要望があった場合、または対象リポジトリで改善すべき課題を見つけた場合のみ提示する。 | true |
| Trinity への課題起票 | 要望があった場合、または Trinity 自体で改善すべき課題を見つけた場合のみ提示する。 | true |

### 6. 後片付け

回答を次の順で処理する。マージの結果が後続の対象を決めるため、この順序を守る。

1. マージ: 選択された PR を `gh pr merge` でマージする。Other 欄の修正要望が指す PR は選択から除外して据え置く。
2. 課題起票: 選択された課題を `gh issue create` で登録する。修正要望のあった単位に紐づく課題は、その単位の作り直しが終わってから改めて確認する。
3. 修正要望: Other 欄に記入があれば、その単位の `requirement.md` へ `## 修正要望` の見出しで本文を追記し、空の `<RUN_DIR>/redrive` を作る（作り直しの合図。新しい `passed` / `failed` に達したとき `loop.sh` が消す）。「3. 実行」の手順で `loop.sh` を再起動して終了状態まで見届け、`passed` に達したらコミットを push する（同一ブランチのため既存 PR は自動更新される）。そのうえで、その単位をマージするかどうかを改めて `AskUserQuestion` で確認し、本手順の先頭へ戻る。
4. 片付け: マージされた単位だけを対象に、`git-flow` スキルに従ってブランチ（リモートを含む）と worktree を削除し、`RUN_DIR` を消す。マージされなかった単位は PR・ブランチ・worktree・`RUN_DIR` をすべて残し、その旨をユーザーに伝える。すべての単位を消したときは `SESSION_DIR` も消す。
